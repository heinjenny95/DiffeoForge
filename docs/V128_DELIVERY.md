## Persistent desktop startup

Long-running owner-authorized jobs should use the installed desktop executable
opened through the ordinary Windows shell, with checkpoint continuation through
the app's existing recovery/resume controls. A scientific GUI hosted inside an
assistant-owned Python interpreter is not an independently installed-app launch,
even when its widgets and execution worker match the verified bundle. Avoid that
operational launch path for persistent computations.

Verify the executable, creation time, Windows-shell parent chain and native run
identity. A generic `IsProcessInJob` result does not identify the owner of that
job and must not alone be interpreted as assistant supervision. Keep the app's
own worker containment intact. After an unexpected interruption, first establish
that no process is writing, preserve the latest durable checkpoint and evidence,
then use canonical recovery and a separate immutable successor. Resume may lose
work since the last saved checkpoint and reinitializes native optimizer history;
it must retain existing reviews and scientific settings.

This is an operational workflow correction. It changes no runtime source or
scientific equations and needs no identical rebuild or version bump. An actual
external-app update during a live scientific run is not used as a verification
test; process independence and numerical completion remain distinct claims.
